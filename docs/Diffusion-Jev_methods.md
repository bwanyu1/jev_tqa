# Diffusion-Jev：何を作り、何を学習したか

2026年10月25日追補。集計結果は [レポート](Diffusion-Jev_report.md)、実行の経緯は [開発記録](DEVELOPMENT_LOG.md) を参照。

## 出発点：構造化出力とJevは相性がよいのではないか

DiffusionGemma論文§9.3・付録G.3は、JSONなどの構造的な事前知識を並列生成に利用し、少ない反復で出力を完成できることを示している。そこで「Choice / Noul / Scoreという型があり、同じ状態に複数の問いを付けて確率付きで返すJev型の判定なら、この性質を生かせるのではないか」と考えた。これは研究の動機となる仮説であり、構造化すれば常に精度が上がるという主張ではない。

出典：[DiffusionGemma Technical Report §9.3・付録G.3](https://arxiv.org/html/2608.00146v1#S9.SS3)。本実験はGemmaの重みそのものを使わず、Qwen3-VL-4B-Instructへ手順を移したもの。本物のJevとの性能比較でもない。

## 拡散化①：左から書くモデルに、全体を修復する計算経路を作る

元の自己回帰モデルは `p(y|c)=∏ᵢp(yᵢ|c,y<ᵢ)` と、文脈cと既に書いた接頭辞から次のトークンを予測する。拡散側は、壊れた回答キャンバスxₜから元の回答x₀を予測する。

`model.py`では、文脈を因果注意で読んでKVキャッシュを作り、キャンバス側だけを双方向注意にする。同じバックボーンの重みを共有するが、自己条件付けのFFWは追加する。「重みを一切増やさない」という説明は正確ではない。画像・動画は文脈側に入り、今回の追加学習はテキストだけ。

キャンバス全体の予測を次の反復で直せる点が、1トークンずつ確定する通常の自己回帰と異なる。長い回答では、完成済みのブロックを文脈へ足すブロック自己回帰を使う。

実装：`djev/model.py` の `encode / decode / forward_train`、`djev/sampler.py` の `generate`。

## 拡散化②：一様ノイズから元の回答へ戻す学習

学習時にはノイズ率 `t ~ U[0,1]` を引き、回答の各位置を確率tで語彙中の一様ランダムなトークンに置き換える。

`q(xₜ,ᵢ|x₀,ᵢ) = (1−t)δ(xₜ,ᵢ=x₀,ᵢ) + t/|V|`

これは `[MASK]` を置く吸収型拡散ではない。正解の回答は変わらず、毎回異なる壊し方をした入力から正解トークンを交差エントロピーで復元する。汎用段階はデコーダの復元損失のみ（`--no-encoder-loss`）。50%の例には直前の予測分布を埋め込みへ戻した `z = FFW(p̂₀E)` を与え、残りはz=0とする。

推論時はランダムなキャンバスから開始し、確信の高い位置を残して迷う位置を再サンプルする。温度を0.8から0.4へ下げ、低エントロピーかつ予測の安定で停止する。汎用自由文は最大N=192、最終穴埋め評価は最大N=48で、上限と実際の推論回数は異なる。

実装：`djev/sft.py:diffusion_loss`、`djev/sampler.py`。

## 拡散化③：用意したのは「質問＋普通の回答」

| 段階 | データと教師 | 学習設定 |
| --- | --- | --- |
| v1 | UltraChat由来の英語指示に元のQwenが回答、約12,000件 | 3,000ステップ |
| v2 | v1の回答＋GPT-OSS-20Bの英語回答約12,000件、計約24,000件 | v1から6,000ステップ |
| v3 | 日本語指示へ元のQwenが回答した15,000件＋英語混合から15,000件 | v2から4,000ステップ |

生成した主要な回答群は英語約24,000件＋日本語15,000件、約39,000件。これを一度に39,000件で学習したわけではなく、v3の投入ファイルは日英30,000件。少量のGroq生成分もスクリプトの混合対象なので、件数は概数で示す。

JSONLの構造は `{"messages":[{"role":"user","content":"指示"},{"role":"assistant","content":"教師の回答"}],"truncated":false}`（形式説明用であり実測行ではない）。教師の回答を新たな正解として、壊して戻す練習をする。元の事前学習コーパスを再学習したものではない。

共通設定：文脈512、回答256×最大2キャンバス、batch 2、LoRA rank 64、勾配チェックポイント。長すぎる文脈は除外。生成上限で途切れた回答は `truncated` を付け、完全な256トークン単位だけを終了トークンなしで使用する。完結した回答の最後のキャンバスは終了トークンで埋める。

確認先：`scripts/run_general.sh`、`scripts/pipeline_v3.sh`、`scripts/pipeline_ja.sh`、`djev/distill.py`。

## Jev化①：文章の生成を、型付きの複数判定へ変換

入力は `state`（判断する文章など）と `questions`（型・ID・問い・候補）、教師は `answers`。Choiceは選択肢番号、Noulはtrue/false、Scoreは離散的な段階番号を使う。Choice / Scoreは2〜9候補であり、Scoreは連続値回帰ではない。

例えばMultiNLIなら、同じ前提文と仮説文に「関係はどれか」「含意するか」「矛盾するか」の3問を付ける。これにより、単にJSONを学ぶだけでなく、同じ状態に対する複数の答えを学習する。選択肢と質問の順番はシャッフルする。

### 用意した判定データ

| データ | 変換後の課題 |
| --- | --- |
| BoolQ | 読解のNoul |
| MultiNLI | 関係のChoice＋含意・矛盾のNoul |
| SST-2 | 感情のChoice＋推薦のNoul |
| AG News | 分野のChoice＋分野別Noul |
| GoEmotions | 複数感情のNoul |
| Civil Comments | 有害度のScore＋属性のNoul |
| CommonsenseQA / ARC | 常識・理科のChoice |
| Amazon日本語レビュー | 星のScore＋好意的かのNoul |

公開9種類から約43,000行、GPT-OSS-20Bの自己一致フィルター済み判定約11,000行、GPT-OSS-120Bの約250行で基礎混合約55,000行。さらにGoEmotions trainから、1状態に8・10・12・14・16問を付けた10,000行を追加して最終約65,000行とした。行数と質問数は別で、複数質問のある1行を1件としている。20B生成ラベルの検証値93.5%は120Bとの一致率であり、真の正解率ではない。

## Jev化②：「JSONを書け」から、明確な穴埋め問題へ

以下は仕組みを伝えるための説明用例であり、モデルの実測入出力ではない。

```text
state: Comment: Thank you, this made my day!
questions:
  gratitude (Noul): Does the comment express gratitude?
  anger (Noul): Does the comment express anger?

与える回答キャンバス: {"gratitude": □, "anger": □}
正解:                 {"gratitude": true, "anger": false}
```

プログラムが括弧・キー・区切りを作るだけではなく、**学習の入力そのものを穴埋め問題にする**。値の位置をslot maskで指定し、その位置だけにランダムノイズを入れ、デコーダ損失もその位置だけで取る。推論でも、反復ごとに既知位置を元へ戻し、未知の値だけを全問まとめて更新する。

`Ldecoder = meanᵢ∈slots CE(pθ(x₀,ᵢ|xₜ,c,z), x₀,ᵢ)`

最終学習の総損失は `Lencoder + Ldecoder`。エンコーダの次トークン損失は文脈と回答の有効位置を対象とするので、「すべての損失を穴だけで取る」は誤り。値が候補ごとに1トークンで表せることをトークナイザで確認し、適合しない行は除外する。

最終設定：`general_v3`から、6,000ステップ、文脈1,024、128トークン×1キャンバス、batch 2、LoRA rank 8、学習率1e−4→1e−5、warmup 100。初期の丸ごとJSON生成版の64トークンと区別する。

## Jev化③：候補上の確率を返す

各穴のlogitから許可候補を取り出し、その候補集合上で再正規化する。

`P(v|question) = exp(logit(v)) / Σu∈候補 exp(logit(u))`

`djev/infill.py:diffusion_decide`はfirst（最初の予測）とfinal（停止時）を保存し、APIの `probs` と `answer` にはfirstを使う。収束後の分布が極端になりやすく、評価ではfirstの較正が良かったためである。これは候補内のモデル確率であり、確率を直接教師として回帰したものでもない。

**評価上の読み方**：90.5%やECE 0.007はfirst読み出しによる。一方、0.55秒・5.7回は反復停止まで計測した値で、firstだけを返して早期終了した速度ではない。反復が最終APIの精度を上げたとは、この結果からは言えない。firstのみで停止する実装の速度比較は未測定。

## Jev化④：比較条件と結果を切り分ける

AR対照も同じ判定約65,000行を6,000ステップ学習し、同じ回答テンプレートの穴を左から順に埋める。固定のJSON文字列をARだけに毎回生成させる比較ではない。ただし拡散は汎用拡散化済みv3から、ARは元のモデルから判定SFTを行うため、全工程の学習計算量が等しい比較ではない。

| k | 拡散：質問正解率 / 全問正解 / 秒 / 回数 | AR：質問正解率 / 全問正解 / 秒 / 回数 |
| --- | --- | --- |
| 1 | 84.0% / 84% / 0.21 / 2.2 | 87.0% / 87% / 0.06 / 1 |
| 4 | 90.5% / 74% / 0.33 / 3.5 | 87.3% / 69% / 0.27 / 4 |
| 8 | 91.0% / 60% / 0.40 / 4.3 | 92.6% / 65% / 0.53 / 8 |
| 16 | 96.3% / 54% / 0.55 / 5.7 | 95.5% / 60% / 1.13 / 16 |

構造化の利点が単発判定やあらゆる精度指標の優位を意味するわけではない。最終2モデルの結果は[レポート](Diffusion-Jev_report.md)にまとめる。

## 最終2モデルの実際の入出力

発表の結果は `jev_infill` と `ar_sft_v5` の2モデルに限定する。保存済みの自由文GIFと画像判定スライドは途中版であり、最終モデルの個別出力として使わない。

最終画像評価の原ログ `logs/img_jev_infill.jsonl`、`logs/img_ar_sft_v5.jsonl` と入力 `data/image_eval.jsonl` を回収し、600行の正解対応を照合済み。写真のあぶみ認識（評価行30）と磁石の距離比較（行78）を採用し、最終2モデルの実際の回答と確率を表示した。両者とも両問正解で、確率は順に拡散93.1%・59.2%、AR99.7%・95.3%。[個別出力の原記録](image_examples_final.json)と[レポート](Diffusion-Jev_report.md)を参照。

画像付き600問の集計は画像の寄与そのものではない。画像なしの同一問題との比較は未実施であり、今後は画像を外す／入れ替える対照と、視覚情報が必要な部分集合で評価する。

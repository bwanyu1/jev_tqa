# 拡散Jevを実際に使ってみた記録

2026年10月25日。最終チェックポイント `runs/jev_infill` をRTX 4060 Ti（16GB）上で実行した。ベンチマーク問題は使わず、問い合わせ振り分けとレビュー属性抽出の架空の業務文を今回9件書いて投入した。実顧客のログではなく、小規模な手動試用である。学習の追加・正解率の採点・実際の返金や振り分けの実行はしていない。

続けて履歴・期限・例外・システム連携を含む24回の追加試用を行ったところ、業務上重要な誤判定と入力長の実装不具合が見つかった。[実務上の課題の追補](Diffusion-Jev_operational_findings.md)を併せて参照。

## 使ってみた印象

**決めた項目を一度に判定して、後段のプログラムへ渡す部品として使いたい。** 日本語でも今回の問い合わせの担当・優先度・返金の有無を拾えた。何を判断させるか、候補と判断ルールを先に決めておく作業は必要だった。

問い合わせでは、担当4択・優先度3択・返金要求の有無・二重請求の有無・全停止の有無・口調3択の計6項目を一度に依頼した。業務ルールは入力のstateに記載し、今日が期限または現在の完全停止なら至急、内容も時期も不明なら情報不足、とした。入力本文が日本語の場合も、ルールと判定質問は英語。すべてを日本語にした運用は今回は試していない。

## 実際の入力と返り値

### 二重請求を、担当と対応事項へ分解する

本文：

> 注文A104の代金が二重に引き落とされました。重複分を今日中に返金してください。

実際の判定（表示用に候補番号を日本語へ戻したもの）：

```json
{
  "担当": "請求担当",
  "優先度": "至急",
  "返金要求": true,
  "二重請求": true,
  "サービス全停止": false,
  "口調": "否定的"
}
```

担当の候補内確率98.6%、至急85.3%、返金要求96.7%、二重請求96.7%。0.411秒、デノイズ4回。読んだ人が後段の振り分け処理へ渡したい情報を、一度の依頼で取り出せた。

### 曖昧な問い合わせで、情報不足を選べるか

本文：

> 例の件、確認してもらえますか。

担当は「一般窓口」72.6%、優先度は「情報不足」74.3%、返金・二重請求・全停止はすべてfalse、口調は中立。0.491秒。情報不足を候補に用意したことで、この例では無理に至急・通常のどちらかへ決めずに済んだ。ただし担当にも「不明」があるとさらに運用しやすそうで、候補の設計が重要だと感じた。

### 不具合があっても、最終的には満足したレビュー

本文：

> 最初に届いた品は電源が入らず返品しました。でも交換品は快適に動いています。対応も早かったので、今は買ってよかったと思っています。友人にも勧めたいです。

「購入を推奨する」99.6%、「不具合の報告あり」81.8%、「全体の感情は肯定的」99.4%。0.228秒。単に良い／悪いにまとめず、全体の満足と過去の不具合を同時に拾えた。ただし「現在の交換品にも不具合があるか」とは別の質問なので、業務に使う質問の時点・対象は明示する必要がある。

### ほかに試した入力

| 入力 | 実際の主な判定 | 応答時間 |
| --- | --- | --- |
| 英語の二重請求・今日中の返金依頼 | 請求担当、至急、返金あり、二重請求あり | 5.648秒（初回） |
| 英語の追跡番号の問い合わせ、急ぎではない | 配送担当、通常、返金なし | 0.436秒 |

本文中の分類指示を含む例は、この1件では業務ルールどおりに判断できた。これを根拠に、指示の混入全般に強いとは評価しない。

## 使ううえで気になったこと

**確率をそのまま運用の閾値へ使うのは早い。** 英語の二重請求依頼では、本文に明確に `today` があるのに、優先度が至急52.5%・通常46.4%だった。同内容の日本語では至急85.3%。配送担当の確率も英語59.2%に対し日本語94.1%だった。両方とも選ばれた答えは同じだが、仮に80%未満を人へ回すと、言語で扱いが変わってしまう。この確率差は各入力1回の観測で、言語差の一般的傾向や安定性を証明するものではない。

**起動の重さも実際に感じた。** キャッシュ済みモデルと段階的なアダプターの読み込み・結合に153.7秒。最初の依頼はさらに5.648秒かかり、それ以降の8依頼は0.228〜0.506秒だった。モデル常駐後の短い待ち時間はよいが、依頼ごとにプロセスを起動する使い方はつらい。測定はモデル内の処理時間で、HTTPサーバーやネットワーク越しの利用時間ではない。起動時にオンラインのモデル確認が長引いたため、最初のプロセスを終了し、キャッシュを使うオフライン設定で実行し直した。153.7秒はその再実行時の値。

出力は候補番号・真偽値と候補内確率なので、画面へ出すにはラベルへの変換が必要。判断理由や自然文の返答は今回の呼び出しでは得られない。今回の9件では妥当な判定を返したが、実データでの検証と保留の設計は別途必要になる。

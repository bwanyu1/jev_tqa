# 今後の課題：能力・学習・定義と、動画アノテーション

2026年10月25日更新。日本語改善・汎用自由文のSD·RLという元からの課題を継続し、実務試用で見つかった問題と、動画への応用を加える。実動画1本の最小試用を実施した。[実際の入力・出力](Diffusion-Jev_video_practical.md)では、正順の状態変化に手応えがある一方、両モデルの逆順方向の誤判定、静止画での時刻状態の推測、拡散finalの悪化が見られた。以下の広範な学習・評価は今後の計画であり、動画で強いと確認した結果ではない。

## 主要な仮説を2つに整理する

第一は、**元モデルの能力と、必要な課題に対する追加学習の不足**。今回の汎用拡散化・判定SFTのデータはテキストで、視覚的な細部の照合や動画の動作ラベルを直接学習していない。実務試用の失敗が元の能力に由来するか、拡散化・判定SFTで失われた能力か、課題固有の追加学習が足りないかは、まだ分離できていない。

第二は、**何を正解として判定させるかの定義**。「同じ物」は同じカテゴリ・同じ仕様や外観・同じ物理個体で異なる。「接触」「把持成功」も見た目だけで確定できるとは限らない。現在と過去、観察と次の行動、確認済みと条件付きの主張を分け、見えない・該当なしのラベルも必要になる。

これは失敗原因の確定ではなく、次の実験の軸である。入力長超過によるCUDAエラーのような確認済みの実装不具合は、この2仮説と別に修正する。

### 切り分け方

最終結果の主比較は拡散Jevと同じ判定SFTを行ったARの2モデルのままとする。原因を調べる補助実験では、元のQwenも同じ入力・同じ定義で確認する。

| 確認する比較 | 分かりそうなこと | 断定できないこと |
| --- | --- | --- |
| 元モデル・AR・拡散で同じ動画と質問を使う | どの段階・経路で失敗が出るか | 全モデルが失敗しても、能力不足だけが原因とは限らない |
| 定義を曖昧な問いから明示的な問いへ変える | 問いと候補の定義への依存 | 1例の改善だけでは一般的な定義の良さは確定しない |
| 定義を固定し、少量の課題SFTの前後を比べる | 追加学習で改善する余地 | 改善しないだけで、元モデルの限界とは断定できない |
| 静止画、正順動画、逆順動画を比較する | 時間的な情報を利用しているか | 同じラベルを返すべき状態と、順序で変わるイベントは別に設計する |

フレーム抽出・動画デコード・プロンプトや画像順の問題も確認し、モデルの能力と入力処理の不備を混同しない。

## 元からの課題を残す

### 日本語とトークナイザ

同じ意味の日英で、答えだけでなく候補内確率も確認する。文字を断片へ分けるトークナイザと並列復元の相性は継続課題。文字断片を再推定するサンプラーを試し、日本語向きのトークナイザを持つ基盤でも検証したい。既存候補のGemma 4 E4Bでは、自己条件付けと層ごとの埋め込み（PLE）の両立への対処が先に必要。

日本語で妥当な判定を返した試用例もあり、一律に日本語が使えないわけではない。一方、英語でも残る時点・例外条件の誤りを、日本語の改善だけで解決する課題にはしない。

### 汎用自由文のSD·RL

先生を固定し、元のモデルから離れすぎない正則化を入れて再検証する。目標は同じ問題でN=48の品質をN=192に近づけ、反復を減らしても文章品質や繰り返しを悪化させないこと。既存の数独での試みを、そのまま自由文の成功と扱わない。

これは最終の穴埋め判定モデルとは別の汎用生成の課題であり、最終2モデルの判定結果に混ぜない。動画アノテーションを先に進める場合も、元の課題から削除せず研究項目として残す。

## 動画で並列処理を活かす仮説

**動画を全編参照し、各時間窓のラベル列をまとめて穴埋めする**形は、拡散Jevの応用候補として有望に見える。例えば6つの窓に、接近・接触候補・持上げ・運搬・解放・静止という状態候補を同時に割り当てる。これは説明例であり、今回得られた実測出力ではない。

```text
入力：参照物＋時刻付き動画フレーム列
出力の未知部分：{"t1": □, "t2": □, "t3": □, "t4": □, "t5": □, "t6": □}
各穴の候補：接近／接触候補／持上げ／運搬／解放／静止／落下／不明
```

同じ反復で複数窓の出力を更新でき、デコーダ内では前後のラベルを参照できる。ただし、現状の試用でも複数の判定が矛盾したので、並列更新が時系列の整合を自動的に保証するとは言えない。時系列ラベルを学習させ、定義に沿った評価が必要になる。

現行の最終APIはfirst（初回予測）を返しており、反復後のラベル列を返していない。したがって、前後の予測ラベルを参照する反復が実際のアノテーションの整合性へ効くかは、firstとfinal（停止時）の読み出しを比べて評価する。finalの確率が極端になりやすい既存の観測もあるので、一貫性だけでなく誤ラベルと確率も確認する。

並列性が期待できるのは主に**出力ラベルの更新側**。動画の読み込み、フレーム抽出、映像特徴の計算、入力文脈のエンコードのコストがなくなるわけではない。また、オフラインで全編を渡すならARも未来のフレームを参照できる。拡散だけが全編を見られるという比較にはしない。

まず全編を参照できるオフラインの教師データ候補生成から試す。リアルタイムでは未来のフレームが未到着なので、同じ条件では扱えない。

## フィジカルAI向けアノテーションの最初の検証案

対象は短い把持・運搬・置く動作の動画。実ロボットのカプセル運搬動画1本について、最終拡散とARに各6条件を渡し、動画入力からラベル保存までを確認した。25フレームを参照し、正順・逆順・最終静止画、3/6/12時刻、first/finalを比較した。逆順の方向と不明判定は課題として残り、速度優位も確認できなかった。その後、正常・把持失敗・落下・遮蔽・作業なし・繰り返し動作を含むクリップへ広げる。

### 先に決めるラベルの契約

| 項目 | 暫定的な扱い |
| --- | --- |
| 対象物 | 参照画像や物体IDを指定。カテゴリ一致と同一個体を区別する |
| 時間単位 | 固定長の窓を切り出し、窓の開始・終了時刻を保持する |
| 状態とイベント | 「保持している」という状態と「持ち上げ開始」というイベントを別に定義する |
| 接触 | 映像から分かるのは接触して見える候補。力や真の接触状態を推測で確定しない |
| 把持・持上げ | 支持面から離れ、把持器と相対位置を保って移動する等の観察基準を、人が決める |
| 成功 | 目標領域・解放後の状態・必要な継続時間を、動画と作業ごとに先に指定する |
| 遮蔽・画角外 | 不明を用意し、見えないものを否定や失敗に自動変換しない |
| 出力 | Choice / Noul / Scoreの短い内部IDで返し、時刻はプログラムが窓の時刻と結び付ける |

秒数のしきい値や許容する境界ずれは、動画のFPSと作業速度を見て決める。モデルが自由に時刻文字列を生成する前提にはせず、既存の型付きAPIに合わせて区間ラベルを付ける。

### 何を見るか

人が付けたラベルとイベントの境界に照合し、成功と誤判定する例、遮蔽で不明を選べない例、ラベル列の時間的矛盾を確認する。人同士でも定義が揃うかを先に見る。

同じクリップで、単フレームのみ、正順、逆順を比較する。窓数も少数から増やし、拡散とARで、ラベルの一致・境界・矛盾・所要時間がどう変わるかを見る。失敗クリップも含め、静止した最終状態だけを見て成功扱いしていないか確かめたい。

速度は、動画デコード・映像特徴・文脈のエンコード・ラベルのデノイズ・保存処理を分け、最後に全体時間を比較する。6画像で入力1,658トークンになった既存試用もあるため、動画のフレーム数と入力長、回答枠128の制約も先に点検する。

生成ラベルはまず人が確認する教師データの候補とし、モデルの確率だけで正解ラベルとして採用しない。クリップ参照・時刻・定義版・モデル版・人の修正を保存する。実ロボットの制御を行う検証ではない。

## 順次入力と拡散出力を分けて検証する

新しい映像フレームを時間順に読み足し、過去の文脈をキャッシュとして再利用する。その文脈から、直近の複数区間のラベルを拡散でまとめて更新する案を検証する。入力の毎回の再読を減らしつつ、複数区間の答えを整合させられるかを見る。これは未実装・未検証の仮説であり、最良の構成だと確認した結果ではない。

現行も入力は因果方向のエンコード、回答側は拡散更新。新しい点は順次入力・キャッシュの継続利用・更新窓の設計となる。既存のオフライン動画試用は全編を一度に渡しており、ストリーミングの検証ではない。視覚処理・時刻位置・キャッシュの互換性も実装時に確認する。

同じ映像範囲・フレーム数・入力キャッシュ・ラベル定義を使い、AR出力と拡散出力を比較する。起動時間を除き、入力処理、ラベル更新、全体の待ち時間を別に測る。人手ラベルとの一致、動作境界のずれ、不明判定、後から出力を修正する頻度、人の修正時間を評価する。未来の映像を使えないオンライン条件と、全編を見られるオフライン条件は分ける。
